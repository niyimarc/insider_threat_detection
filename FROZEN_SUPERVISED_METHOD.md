# Frozen supervised insider-threat detector

This file fixes the method BEFORE the locked test users are scored. The final script
(`scripts/supervised/final_detector_locked.py`) refuses to run without this file, records its
SHA-256 in its report, and whatever the locked result is, it is the result that is reported.
Do not edit this file after the locked run; if the method must change, that is a new method and the
locked users are no longer a fair test of it.

## What is frozen

**Data unit.** One row per user per calendar day on which the user had any logon, device or file-copy
activity (`src/supervised/all_days.py`). Training label = the insider's window from `insiders.csv`
(a day inside the window is positive). Input columns = every column of the `all` signal configuration
(file, device, logon, http) of `src/supervised/feature_sets.py: ALL_DAYS`; the exact list and its hash are
printed in the report. Day-level logon and device features use causal per-user baselines (trailing 28 active
days, minimum 7).

**Models (two, both reported, neither chosen afterwards).**

| name | model | settings (not tuned) |
|---|---|---|
| gradient_boosting | scikit-learn `HistGradientBoostingClassifier` | depth 3, learning rate 0.05, 200 rounds, min leaf 40, L2 1.0, no early stopping |
| gru | one-layer GRU over the user's previous 14 active days (today last) + linear head | 32 hidden units, Adam lr 2e-3, weight decay 1e-4, 10 epochs, batch 256 |

**Training.** Each model is trained on ALL development users (the 50 users of the `dev` partition: 35 insiders,
15 benign) with class-balanced weights replaced by DATE-MATCHED weights (7-day calendar strata, so the model
cannot use the date), for seeds 0, 1 and 2; the day score is the mean over the three seeds.

**Day -> person.** A person's score = the mean of their 7 highest day scores (secondary rule: their single
highest day).

**Alert cutoff.** The 99th percentile of the BENIGN development users' OUT-OF-FOLD day scores, from the same
model family trained date-matched with 5 user-level folds x 3 repeats (fold seed 0). The cutoff is set on
development data only and applied unchanged to the locked users.

**What will be reported on the locked users, for both models, with 95% user-level intervals.**

1. Whole-timeline person ranking: user-level AUROC (insiders vs benign users) with both person-score rules, and
   how many of the top 5 / top 10 ranked users are insiders next to the random baseline.
2. Matched-period check: each insider's score over their own window against every benign user's score over the
   same calendar dates.
3. Alert simulation with the frozen cutoff: insiders detected inside their window, days to first alert, insiders
   alerted before their window, benign users alerted.
4. Day level: the insiders-only, date-stratified AUROC (insider window days against the same insiders' other
   days in the same week).
5. The two controls (same model given only the date, or only the user's own clock) for 1, 2 and 4.
6. The ranked user list (CSV).

The answer key is used for EVALUATION labels only (as on the development partition); no feature, model or
threshold is built from it.

## Disclosures that go with every result

* The method was designed, debugged and compared on the development partition; development numbers are optimistic.
* The locked partition was already used once, for the UNSUPERVISED models (their results are known to the
  author). It has never been used to train, tune or select anything in the supervised work. This is the first
  and only look at the locked users by the supervised detector.
* Choosing gradient boosting and the GRU as the two frozen candidates followed development results; the
  configuration ("all signals", date-matched training) was fixed before the locked run.
* Scenario 2 contributes most of the malicious days; scenarios 1 and 3 are too small to evaluate separately.
* CERT r4.2 is simulated: the insiders are scripted. The share of insiders in these data is far above any real
  organisation.
